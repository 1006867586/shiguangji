# 点餐小程序后端上云改造方案

> 目标：把原点餐小程序单体 `Express + SQLite + WebSocket` 的 mock-server 改造成
> 「**EdgeOne Edge Functions（无状态函数）+ Supabase Postgres + Supabase Storage 对象存储**」的云原生架构，
> 使其可以部署在 EdgeOne 上，而不再依赖本地进程常驻。
>
> 代码源：`D:\坚果云\我的坚果云\ai code project\diancan\diancan\mock-server\`（server.js ~102KB、db.js、config.js、wechat-push.js 等）

- 现状技术栈：Express 4 + better-sqlite3 + ws + 内存 Map 缓存
- 目标技术栈：EdgeOne Edge Functions + **Supabase Postgres** + Supabase Storage
- 关联前端：小程序 `utils/ws.js` 已改为**轮询**实现（保留原接口签名），后端不再需要长连接

---

## 1. 为什么必须改造（现状痛点）

| 问题 | 具体表现 | 对 Serverless 的影响 |
|------|---------|---------------------|
| **本地 SQLite 文件** | `data.db` 存在函数实例本地磁盘 | Edge Function 是**无状态、可迁移**的实例，本地文件会在实例回收后丢失、且多实例间不共享 |
| **内存 Map 当主读缓存** | `loadAll()` 启动把 14 张表读进内存 Map，读走 Map、写回 DB | 内存随实例销毁；多实例并发写 DB 会用旧 Map 盖掉新数据 |
| **WebSocket 长连接** | `WebSocketServer({ noServer: true })` 按 openid 分组推送 | Edge 函数无常驻进程，无法保持长连接；**已由前端轮询替代** |
| **图片 base64 存 SQLite** | `uploads.data` 列存 base64，图片经 `/upload/:id` 回读 | base64 体积膨胀、无法走 CDN；应迁移到 Supabase Storage |
| **Express 单体路由** | 63 条路由 + 中间件全在一个进程 | Edge 函数按路由拆分、按需冷启动 |
| **微信内容安全回调** | `/wx-callback/media-check` 需要公网 URL 验签 | 需提供固定公网地址（Edge 函数可承载） |

## 2. 目标架构

```
小程序(front-end, 原生)
   │  https
   ▼
EdgeOne（CDN + Edge Functions 网关，域名 diancan.yourdomain.com）
   │ 按路由前缀分派
   ├─ fn-auth     /auth/*  /me/*  /pair/*
   ├─ fn-menu     /categories/*  /dishes/*  /upload*
   ├─ fn-shop     /shop/*
   ├─ fn-recipe   /recipes/*
   ├─ fn-order    /orders/*
   ├─ fn-notify   /notifications/*  /wx-callback/*
   └─ (dev)       /debug/*  /admin/*     —— 仅预发环境，生产可不部署
   │
   ├──► Supabase Postgres（业务数据，免费档可 0 元起步）
   └──► Supabase Storage（图片对象存储）
```

### 2.1 技术选型结论

- **计算**：EdgeOne Edge Functions（轻量函数，按调用量计费，免运维）。因为前端已改轮询、后端已 `stateless`，满足函数运行条件。
- **数据库**：**Supabase Postgres**（托管 PostgreSQL）。
  - ✅ 有长期 **免费档（Free tier）**：500MB 数据库、每月若干请求额度、支持 RLS，**可 0 元起步**。
  - 与原 SQLite 的 SQL 语法差异小（`TEXT`/`BIGINT`/`JSONB` 与现状高度对齐），改造成本低。
- **图片存储**：**Supabase Storage**（对象存储，免费档自带额度），替代 `uploads` 表的 base64。
- **微信登录/推送**：接口不变（`code2session`、`subscribeMessage.send`），仅需正确配置 `WECHAT_SECRET` 等环境变量。

## 3. 数据库迁移（SQLite → Postgres）

### 3.1 表清单与类型映射

现状 `db.js` 共 **14 张表**。迁移目标 Postgres（Supabase），`snake_case` 列名**保持不变**以复用全部 `*RowToObj` 映射函数。

| SQLite 类型 | Postgres 类型 | 说明 |
|------------|--------------|------|
| `TEXT PRIMARY KEY` | `TEXT PRIMARY KEY` | openid / code / id（openid 与各种 `upl_`/`bnr_` 前缀短串，TEXT 主键即可，无需转 VARCHAR） |
| `INTEGER`（时间戳 epoch ms） | `BIGINT NOT NULL` | created_at / updated_at，保持毫秒值，避免改代码 |
| `REAL`（价格） | `NUMERIC(10,2)` | price / total_price |
| `INTEGER`（布尔 0/1）| `SMALLINT`（0/1）或 `BOOLEAN` | available / status 相关。若用 `BOOLEAN`，需同步改 mapper 里 `r.available === 1` 的判断；用 `SMALLINT` 则 mapper 零改动 |
| `TEXT`（JSON 串） | `JSONB` | items_json / recipe_json / steps_json / ingredients_json / payload_json / notice |
| `TEXT`（base64 大数据） | 删除（迁 Supabase Storage） | uploads.data 列不再需要 |

建议 JSON 列（items_json、steps_json 等）用 `JSONB`（Postgres 原生，支持查询与 GIN 索引）。

### 3.2 三张表额外说明

- **uploads**：保留表但**只存元数据** `(id, mime, scope, size, object_key, created_at)`，删除 `data` 列；真实图片以 `object_key` 指向 Supabase Storage。所有 `*UploadId` 关联表（dishes.thumbnail_upload_id、shop_configs.logo_upload_id、shop_banners.upload_id）逻辑不变。
- **notice**：`shop_configs.notice` 存 JSON 数组字符串。Postgres 用 `JSONB` 列，`parseNotices`/`stringifyNotices` 逻辑复用。
- **tokens / notification_subscriptions**：有 `UNIQUE`/复合 PK 的表，建表约束需同步（见 §3.4）。

### 3.3 驱动替换：`better-sqlite3` → `pg`

现状 `db.js` 使用 `better-sqlite3` 的**同步 API**（`.prepare().get()/.all()/.run()`），且默认 `foreign_keys = ON`。
迁移到 Postgres 必须做两处改造：

1. **同步 → 异步**：把 `const row = stmt.get()/stmt.all()` 改为 `const result = await pool.query(...)`（`pg` 返回 `{ rows }`，单行取 `rows[0]`），原 `saveXxx/clearXxx/listXxx` 函数改为 `async`。
2. **占位符语法**：SQLite 的 `?`/`@named` 改为 Postgres 的 `$1,$2,...`（`pg` 参数化按序号）。

> ⚠️ **最大改造量在 `db.js`**：需把约 60 个 `stmt` + 20+ 个公共函数全部异步化，并把每个 SQL 占位符从 `?` 改成 `$n`。
> 建议保留 `db.js` 作为**唯一的 DAO 接口层**，`server.js` 的路由只调用 `db.saveX(action)`，不要在每个函数里散落 SQL。

参考最小改法（保留既有函数名与入参形状，只把实现换成异步）：

```sql
-- Postgres 版 schema（节选，执行于迁移脚本 schema.sql）
CREATE TABLE IF NOT EXISTS users (
  openid       TEXT PRIMARY KEY,
  nickname     TEXT NOT NULL,
  avatar_url   TEXT NOT NULL DEFAULT '',
  pairing_code TEXT,
  created_at   BIGINT NOT NULL,
  updated_at   BIGINT NOT NULL
);
```

```javascript
// db.js 异步改造示意（pg/Pool）
const { Pool } = require('pg')
const pool = new Pool({
  connectionString: process.env.DATABASE_URL, // Supabase 连接串，内置 ssl=require
  connectionTimeoutMillis: 5000,
})

async function saveUser(u) {
  const { rows } = await pool.query('SELECT openid FROM users WHERE openid = $1', [u.openid])
  if (rows.length) {
    await pool.query(
      'UPDATE users SET nickname=$1, avatar_url=$2, updated_at=$3 WHERE openid=$4',
      [u.nickname, u.avatarUrl || '', u.updatedAt || Date.now(), u.openid]
    )
  } else {
    await pool.query(
      `INSERT INTO users (openid,nickname,avatar_url,pairing_code,created_at,updated_at)
       VALUES ($1,$2,$3,$4,$5,$6)`,
      [u.openid, u.nickname, u.avatarUrl || '', u.pairingCode || null,
       u.createdAt || Date.now(), u.updatedAt || Date.now()]
    )
  }
}
module.exports = { pool, saveUser, /* ... */ }
```

> 可用 upsert 简化"先查后插"：Postgres 支持
> `INSERT INTO ... ON CONFLICT(openid) DO UPDATE SET ...`，比 SQLite 的 `saveUser` 分支更简洁。

### 3.4 索引与约束（对照迁移）

| 原表 | 原索引/约束 | Postgres 迁移 |
|------|------------|--------------|
| tokens | idx_tokens_openid | `CREATE INDEX idx_tokens_openid ON tokens(openid);` |
| pairings | idx_pairings_merchant / customer | 两复合索引照搬 |
| categories | idx_categories_merchant (merchant,sort) | 照搬 |
| dishes | idx_dishes_merchant_cat | 照搬 |
| orders | idx_orders_customer / merchant | 照搬 |
| uploads | idx_uploads_scope | 照搬 |
| shop_banners | idx_banners_merchant (merchant,sort) | 照搬 |
| recipes / recipe_versions | recipe_versions `UNIQUE(recipe_id,version)`，idx_{} | 照搬 |
| notification_subscriptions | `PRIMARY KEY(user_openid, template_id)` + idx_subs_user | 照搬 |

> **RLS 提醒**：如果仅把 Supabase 当纯托管 DB、函数用 `service_role`/`postgres` 直连访问，则需**关闭 RLS 或授权 service_role**（service_role 本身默认绕过 RLS）。若想启用 RLS 做应用层安全，务必对每张表配置 Policy，否则在 Supabase 后台查不到数据（RLS 未放行时对匿名/受限角色返回空）。
> 本方案简单起见：**函数直接用 service_role 连接、RLS 不强制**，安全主要靠函数只在可信入口暴露。

### 3.5 事务处理（异步化关注点）

原代码多处用 `db.transaction(cb)` 实现原子操作：
- `deleteDishes(ids)`：按 id 逐个删
- `reorderBanners()`：按 ids 顺序重写 sort
- `deleteRecipe()`：删菜谱 + 删所有版本
- `clearRecipes()` / `migrateLegacyRecipes()`

Postgres 下用**客户端级事务**改写（从池子借一个 client）：

```javascript
async function deleteDishes(ids) {
  const client = await pool.connect()
  try {
    await client.query('BEGIN')
    for (const id of ids) await client.query('DELETE FROM dishes WHERE id = $1', [id])
    await client.query('COMMIT')
  } catch (e) {
    await client.query('ROLLBACK'); throw e
  } finally {
    client.release()
  }
}
```

> `reorderBanners` 用一条 `sql` 批量重写会更稳（避免逐行 UPDATE），可在改造时顺手优化。
> `migrateLegacyRecipes()` 是启动时的一次性数据迁移，正式建库时在 SQL 脚本里完成，无需保留运行时函数。

## 4. 内存 Map 迁移策略

`db.js` 中 `loadAll()` 启动时把全部表读进内存 Map，`server.js` 大量直接读这些 Map。
Serverless 下**必须全部改为数据库直查**。逐 Map 处理：

| Map（loadAll 返回键） | 使用场景 | 迁移方式（改为 DB 查询） |
|----------------------|---------|--------------------------|
| `users` | 登录/`/me`/配对时查用户 | `SELECT * FROM users WHERE openid=$1` |
| `tokens` | `auth` 中间件校验 token | `SELECT openid FROM tokens WHERE token=$1 AND expires_at>$2` |
| `pairingCodes` | 配对码查询/防重复 | `SELECT ... FROM pairing_codes WHERE code=$1` |
| `pairings` | 配对关系（merchant→customers、customer→merchant） | 两个带索引条件的 `SELECT` |
| `categories` | 店铺分类列表 | `SELECT ... WHERE merchant_openid=$1 ORDER BY sort` |
| `dishes` | 菜品 CRUD / 顾客点餐 | `WHERE merchant_openid=$1 [AND category_id=$2]` |
| `orders` | 订单列表（双角色） | `WHERE customer_openid=$1` 或 `WHERE merchant_openid=$1 AND status=$2` |
| `uploads`（仅元数据） | 上传回读/校验 | `WHERE id=$1`（只取元数据） |
| `shopConfigs` | 店铺装修配置 | `WHERE merchant_openid=$1` |
| `banners` | 轮播图列表 | `WHERE merchant_openid=$1 ORDER BY sort` |
| `recipes` / `recipeVersions` | 菜谱 CRUD | `WHERE merchant_openid=$1` / `WHERE recipe_id=$1` |
| `subscriptions` / `notificationsSent` | 订阅状态/推送日志 | 原有 `list*ByUser/ByOrder` 直查即可（本就查表） |

**结论**：凡是 `server.js` 里 `.get()/.values()/.filter()` 于这些 Map 的读操作，全部替换为对 §3.3 DAO 的异步查询。改造量集中在 auth 校验、配对、分类/菜品/订单列表这几处高频读。

## 5. 数据库选型与费用（Supabase Postgres）

**免费结论**：Supabase **有长期免费档（Free tier）**，**可以 0 元起步**，这是相对 TDSQL-C 的最大优势。

免费档包含（以官方免费额度为准，随版本可能有细微调整）：
- **Postgres 数据库 500MB**（业务数据量级几十 MB，绰绰有余）
- 每月一定**请求/带宽额度**（对个人点餐低频业务足够）
- 内置 **Auth / Storage / Realtime / RLS**，均可选配
- 免费档项目**暂停**（长时间无请求会自动暂停，再次访问会唤醒），与 Serverless 理念一致

**升级路径**：若后续请求量或存储超免费档，再升到 Pro（按量，约 $25/月起）或按需购买。对当前业务，**免费档足够**。

> 说明：上一版选的 TDSQL-C Serverless 适合"低频、零维护、腾讯云同生态"，但不免费。若你更看重 **0 元成本**且已熟悉 Supabase，选它；连接方式走公网 Pooler 或直连，与 EdgeOne 跨云连通，延迟对低频业务无感。

## 6. 路由拆分清单（Edge Function 划分）

原 `server.js` 63 条路由按业务领域拆成 6 组函数。每组一个部署单元、一份环境变量。

| Edge Function | 挂载前缀 | 包含原路由 | 主要依赖表 |
|---------------|---------|-----------|-----------|
| **fn-auth** | `/auth` `/me` `/pair` | `/auth/login`; `/me`,`/me/joined-merchants`,`/me/guests`,`PATCH /me`; `/pair/code`,`/pair/bind`,`DELETE /pair`,`DELETE /pair/customer`; `/demo/bootstrap` | users, tokens, pairing_codes, pairings |
| **fn-menu** | `/categories` `/dishes` `/upload` | `/categories*`; `/dishes*`,`/dishes/batch-delete`,`/dishes/:id/published-recipe`; `POST /upload`,`GET /upload/:id` | dishes, categories, uploads, uploads→Storage |
| **fn-shop** | `/shop` | `GET /shop/:merchantOpenid`, `PUT /shop`, `/shop/logo-init`, `/shop/banner*` | shop_configs, shop_banners, uploads→Storage |
| **fn-recipe** | `/recipes` | `/recipes*`（含 draft/versions/publish/unpublish） | recipes, recipe_versions |
| **fn-order** | `/orders` | `/orders*`, `/orders/:id/status` | orders |
| **fn-notify** | `/notifications` `/wx-callback` | `/notifications/subscribe`,`/notifications/subscriptions`; `GET/POST /wx-callback/media-check` | notification_subscriptions, notifications_sent |

> **调试/管理接口**（`/debug/*`、`/admin/*`、`/debug/notifications`）仅保留在**预发/本地**环境，生产不部署，避免暴露数据与弱口令风险。

**跨函数广播逻辑注意**：
原 `server.js` 在每个写接口后调用 `broadcastToPairing(...)` 推送 WS。由于前端已改轮询（前端主动拉取+指纹比对），后端这些 broadcast 调用应删除，无需再做事件推送。这一步能显著减少函数间耦合。

> 注：Supabase 自带 **Realtime**（`supabase_realtime` publication），若未来想在这套后端恢复"推数据到前端"，可复用 Realtime 表级推送（与你主项目 shiguangji 的订单实时推送做法一致）。当前轮询已够用，此为其演进选项。

## 7. WebSocket → 无状态（前端已完成）

- 前端 `utils/ws.js` 已改成**轮询**实现，保留 `on/off/connect/close/clear` 接口签名，按事件类型定时拉取 + 指纹比对触发监听器。
- 后端对应动作：**移除 `WebSocketServer` 及所有 `broadcastToPairing` 相关代码**（server.js 中约 25 处广播点）。
- 业务仍能实时/近实时同步：订单状态、菜品/分类/店铺变化、配对关系均靠前端轮询 `listOrders/listDishes/...` 拉取感知。
- 若仍希望更强的实时（可选，不做也不影响上线）：可后续接入微信**订阅消息**或 Supabase **Realtime**，但**当前轮询方案已足够**。

## 8. 图片与静态资源迁移（base64 → Supabase Storage）

### 8.1 现状
`uploads` 表 `data` 列存 base64（无前缀），`GET /upload/:id` 读库返回图片。图片 URL 形如 `{base}/upload/{upl_xxx}`，被菜品缩略图、店铺 logo、轮播图引用。

### 8.2 改造步骤
1. **写入侧**：`POST /upload` 收到 base64/文件后，改为上传到 Supabase Storage（bucket/key），`uploads` 表只存 `object_key`（Storage 路径），不再存 data。
2. **读取侧**：`GET /upload/:id` 返回 302 重定向到 Storage 公网/签名 URL；或直接废弃该接口、让前端用 Storage URL。
3. **存量数据迁移**：`scripts/migrate-data.js` 遍历 `uploads`，把 `data` base64 解码后逐条上传到 Storage，回填 `object_key`，最后删除 `data` 列。
4. **CDN/合规**：Storage bucket 设为**公开读**或走**签名 URL**；微信 `imgSecCheck` 需要公网可访问 https URL，用 Storage 公网 URL（非 `upload/:id`）回调即可。

> bucket 权限建议：图片展示走公开读（`object/public` URL）最省事；若需更私密可设私有 bucket + 签名 URL。本方案默认 `diancan-images` 公开读。

> 前端若仍以 `{base}/upload/{id}` 拼 URL，为兼容可让 `GET /upload/:id` 做临时 302，避免改前端逻辑；后续前端升级为直接存最终 URL。

## 10. 部署指南（EdgeOne + Supabase）

### 10.1 数据库（Supabase）
1. 注册 Supabase、创建项目（免费档）。
2. 在 **SQL Editor** 执行 `schema.sql` 建表（14 张表 + 索引）。
3. 获取连接串：
   - **推荐**：Transaction Pooler（`pg.pooler.supabase.com`）连接串，适合函数并发连接受限场景。
   - 或直连 `db.xxx.supabase.co`（免费档连接数有限，务必用连接池）。
4. 把 `DATABASE_URL` 写入 EdgeOne 函数环境变量（连接串自带 `sslmode=require`）。
5. 若函数用 `service_role` 连接，确保环境变量里有 `SUPABASE_SERVICE_ROLE_KEY`（不是 anon key）；RLS 由 service_role 默认绕过。

### 10.2 图片存储（Supabase Storage）
- 在 Supabase 建 bucket（`diancan-images`），函数用 service_role 上传。
- 建 Policy 允许公开读（图片展示用）或走签名 URL（更私密）。
- 图片 URL = `https://{project}.supabase.co/storage/v1/object/public/{bucket}/{object_key}`（公开读时）。

### 10.3 Edge Function 部署
1. 将 `src/` 按域名分 6 个函数部署到 EdgeOne Edge Functions；或用一个函数按 `event.request.url` path 前缀内部分派（更省资源，适合低频，推荐先这样）。
2. 配置环境变量（见 §10.4）。

## 12. 风险与工作量评估

| 项 | 风险/难度 | 说明 |
|----|----------|------|
| `db.js` 异步化 | 🔴 高、工作量最大 | 60+ 语句 → 参数化异步查询，且占位符 `?`→`$n` 逐一改写，最容易出错；建议 P0 单独做并配自动化测试 |
| 同步→异步调用链 | 🔴 高 | 所有路由回调从同步变 async，`asyncWrap` 需保持，错误处理统一 |
| 内存 Map 读替换 | 🟠 中 | 集中在 auth/配对/列表几处，按 §4 表格逐个换，回归面可控 |
| 图片迁移 | 🟠 中 | 存量 base64 → 存储，量大时注意超时/限速 |
| WS 移除 | 🟢 低 | 前端已改轮询，后端只管删 broadcast |
| 事务改写 | 🟢 低 | 只 4 处事务，按 §3.5 模板改写 |
| Edge 直连 DB 连接管理 | 🟠 中 | 免费档连接数有限，务必用 Pooler/连接池，防冷启动连接泄漏 |
| RLS / service_role 权限 | 🟠 中 | 若在 Supabase 后台配置不当，会出现"表里有数据但客户端查不到"；本方案统一用 service_role，注意分清 anon key 与 service_role key |

**总评**：技术核心改造 = **db.js 同步→异步** 这一件事。完成它后，其余（拆函数、迁存储、部署）都是增量落地。建议按 P0→P5 顺序推进，P0 完成后整个改造风险即大幅下降。
